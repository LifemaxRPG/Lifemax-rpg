## Current baseline

| Area | Presentation | Authority | Web dependency |
|---|---|---|---|

| Character | Web | Core gameplay, web-owned | Required |

These are baseline descriptions, not a claim of complete writer inventory or transaction safety. Native Cash currently delegates commands through 50-native-cash.js, calls existing web operations/save, verifies persisted money and attempts in-memory rollback. Its session-local seen map does NOT establish restart-safe idempotency or atomic whole-gameplay commit. Do not copy that pattern as the new mutation contract.

## Character: first implementation sequence

### C0 — Inventory and deterministic fixtures

Read current character.html, 01/04/07/14/15-runtime.js, later wrappers, navigation, stores and CSS. Produce CHARACTER_INVENTORY.md identifying exact displayed facts/derived values, chart and comparison modes, selection/sorting, skill progression, avatar, weight/BMI, benchmarks and every action/sheet/navigation path. The eight IDs are physique, endurance, intelligence, business, social, discipline, adventure and wellbeing. Benchmark addition is visibly present in the baseline; inventory its complete handler path and any generated attribute-detail actions rather than claiming Character has no mutations.

Use synthetic fixtures for new, established and legacy/ascended states, plus missing/custom/large-history cases. Do not publish personal saves. Measure fixture size and storage headroom; no 5-MB quota assumption is a substitute for handling actual write failure. Capture the current visual and interaction baseline.

### C1 — Build and native foundations

Register direct authored source/test roots idempotently and verify compile/test discovery, inclusion once and rename/removal behavior. Use the existing Compose setup. Add only required theme primitives, manual composition root and one MainActivity destination host coordinated with existing navigation. Preserve existing APK signing, package identity and update flow.

### C2 — Read-only native Character prototype

Finalize the static character projection schema from C0. Implement capability/readiness negotiation, full snapshots and session/projection-sequence freshness through a feature-owned repository and lifecycle-bound transport. No new native gameplay writes or durable bridge metadata solely for this read slice. Snapshot invalidation must observe legacy changes and time-derived values even when durable save revisions do not exist.

Build native charts/cards, selection, comparison and sorting from the authoritative projection and local UI state. Render no Character DOM/captured page in the native presentation. Include loading/error/reconnect states, font scaling, light/dark/accent themes and reduced motion. Native formatting/layout math is allowed; rewards and gameplay calculations remain authoritative.

Integrate behind a persisted native/classic choice with session fallback on unavailable capabilities. An incomplete developer prototype is not a default production replacement. For existing mutating actions, either delegate explicitly to their working web presentation and record that hybrid dependency, or hold default rollout until the native interaction is complete. Never silently omit a button or pretend it saved locally.

### C3 — Lifecycle and acceptance

Verify shared state after real web actions, stale/out-of-order read responses, live/time-sensitive changes, native covering the web authority, navigation/Back, rapid tab changes, background/resume, rotation, process recreation, unreadable/unavailable data and Classic cleanup. Confirm no duplicate hosts, leaks, background render load or transition flash. Record physical-device performance separately from automated/emulator checks.

### C4 — Mutations and full Character interaction parity

Before each native write capability, adopt an operation-specific command/commit/reconciliation design satisfying CONTRACT A14–A15. Audit legacy save handlers and side effects; do not wrap arbitrary global mutations and label them atomic. Test the failure matrix before wiring the control. Replace remaining web sheets/edits and verify both native and existing web consumers observe the same authoritative results without duplicate effects.

Only then label Character native presentation with complete interaction parity. Core authority can still remain web-owned. Retiring that dependency is a separate later cluster cutover.

## Native Character prototype implementation

## Library, Media pane (phase 1)

Native presentation, web authority. `50-native-library.js` (NativeTabKit on view `media`, plugin `NativeMedia`, `library.media.projection.v1`, Settings "Native Library (beta)", off by default) projects the Media pane worded as the page words it: the Media/Journal switch, the header and the four stats, every item (the stored type and status that the filter compares, the page's subtitle and status label, the notes, the link only when it is http or https, and for an item with audio the page's progress label, time and bar and its file line), the filter controls with the page's current filter, the empty and no-match states, the button words, the player state and the feature tip while the page would show it. Search, status and type filters are the screen's own; the page's filter carries a revision that rises whenever the page sets it (typed on the page, or a voice search), and the screen adopts the page's filter whenever that revision differs from the one it holds. `fixtures/media-filter-parity.json` holds the rows the page itself shows for sample filters of the full list, so the screen's filter can be proven identical. Every tap is delegated: the kit closes the screen, the page's handler runs, and the screen comes back (`revisit()`) once nothing it does not draw is over the pane. It never covers the pane while the add/edit form is open, while the audio player is loading, loaded or showing (until a native mini-player exists, so the player's controls never vanish under a screen), while a file button handed to the owner has the focus, while a handed-back tap is still running, or while a level-up plays; it follows these through MutationObservers (one of them on the list, which every save redraws, so a play that fails on the page gives the pane back) and a focusout, never by reassigning a page function, and `blocked()` also reads the page's `audioCtx.loading` flag. The page's toast lies under the screen, so the projection carries it as `notice` while it shows, numbered so that the same words twice are two messages, and a toast that comes while the screen shows is sent at once; the screen draws it as the page's toast (core `PageToast`) once, so every delegated tap comes back with the page's own answer, success or failure. A toast cut short by the screen closing is not shown again, and the toast that names a file button is left out, as it is about the page. The Media writers a tap reaches say honestly when nothing was stored: ticking, removing and removing the audio take the change back when the save fails and report it (`unsavedMessage()`, naming a read-only save as the reason), and the audio file is deleted only after its removal is stored. The Journal stays on the page: the switch's Journal is a web destination, so the screen closes at once and the Journal lock works unchanged.

Phase 0, web only, came first: a reflection or review answer being typed survives a redraw and a relock, and a failed reflection write is reported; `LifeMaxJournalLock.blocksNative()` and `onChange(fn)` are the seam a native Journal will follow (nothing native draws the Journal yet); `mediaUpsert(fields)` is the DOM-free owner of adding and editing, split from the form; voice "journal" and "history" open the Journal; Media has its own tests (`media.test.js`). ## Settings, phase 1, step 1 of 4: the web half (next Native API)

Web authority, no native screen yet. `50-native-settings.js` (NativeTabKit on view `settings`, plugin `NativeSettings`, `settings.projection.v1`, Settings "Native Settings (beta)" under Appearance, off by default) projects the page's own Settings: the head, the five category chips (`SET_CATS`, the chosen one `setCat`), and every card in the page's order with its category (`setCatOf`), its title, its intro and its rows, read from what the page and its renderers have put on the page. So the words are the page's own, a fact a renderer learns asynchronously (the notification permission, the widget count, the food database count, the motor probe) arrives with the next refresh, and a renderer's redraw (an update's progress, "Saving…") refreshes the screen through a MutationObserver on `#view-settings`. A row is one of `row` (title, hint lines, controls), `note`, `text`, `controls` (buttons or the haptic strength standing on their own), `field` (a labelled form field) and `tab` (a bottom-bar row). Every control says how it is operated: `toggle`, `choose` or `press` (a command) or `reveal` (a delegation). The hidden cloud-voice key row never enters the projection. The screen gets a "Classic Settings" row of its own (`classic`), the way back to the page that does not depend on finding the switch (inventory 7.5, hazard 1).

Commands (one per kind of control; each does on the page what a tap on the page's own control does, so every rule stays the page's):

| Command | Payload | What runs on the page |
|---|---|---|
| `toggle` | `{id, on}` | the page's box is set and its own change handler runs: `setLightMode`, every native tab's `setNativeXEnabled`, `setTabTimingToast`, `lmaSetSwipe`, `lmaSetSwipeAnim`, `qfxSet`, `hapSet`, the HD cat's and the voice switch's listeners, `lmaSet` (reminders), `lmaSetBackup('on')`, `lmaHealthSet` (types; the master off), `lmcSet('on', false)`, `lmaTabShow` (bar rows, which refuses the third-last tab with its own toast) |
| `choose` | `{id, value}` | the page's select is set and its change handler runs (`lmaSetScrubSpeed`, `qsfxSetVol`, `dhSetDealMode`, `qartSetPack`, `g3SetPref`, `g3SetDbg`, `lmaSet('lead')`, `lmaSetBackup('days'/'keep')`, `lmaHealthSet('goal')`), or the haptic strength button is clicked (`hapSet` and the double buzz) |
| `press` | `{id}` | the page's button is clicked: the bar's arrows (`lmaTabMove`), "Reset to default" (`lmaTabsReset`), the haptic tries (`hapPlay`) |
| `category` | `{id}` | the chip's own `setPickCat`, so the page shows the same category when the screen closes |

The reply is `{ok, changed, message, saved?, reveal?}`: the page's toast raised by the handler is the message (and is not sent again as a notice); a control the page refused (disabled, an unknown value, the bar's last two tabs) answers `ok:false` with the page's words; a switch that asks Android first (reminders, health sync, calendar import) is turned on only on the page and answers `reveal`. A write that did not reach the device answers `saved:false`: the handler's own write is watched for the length of its synchronous part (where every bound handler writes; lmaSave, setLightMode and the quest keys swallow a failed write), the core save names its reason (`unsavedMessage()`: read-only or full), and the change stays in memory as after the page's own control, which the projection sent with the reply shows.

Delegations (action `reveal` with a control's id): the screen closes, the page switches to the card's category, scrolls the control into view and focuses it, and the screen comes back once the owner's next tap on the page has done its work (350 ms later), unless what that tap opened must stay in front. An id the page no longer has brings the screen straight back. Action `classic` keeps the page in front until the owner leaves Settings.

| Remaining web dependency | How the screen reaches it |
|---|---|
| Text, number and time fields (profile, decay, XP rules, reminder times, quiet hours) and form selects (build, test class) | `reveal`: the field focused; away while a field or select in Settings has the focus; back when it is left (Save's tap included) |
| File pickers (profile picture, Import JSON, trainer pack, USDA file) | `reveal`: the button shown; away from the picker's opening until it reports a choice or a cancel |
| Import JSON | as a picker, then away until the page empties the file input (done, cancelled or failed) and while a reset or import backs up first (`saveReplacing`) |
| Rewards sheet, voice diagnostics, dev chat, onboarding preview, tutorial | `reveal`: the button; away while the sheet or overlay is up (the kit's `lmaTopOverlay`, plus `#devChat.open` and `.luov`); back when it closes |
| Update buttons, backup folder and "Back up now", widget buttons, health and calendar sync, "Capture all" (away while it runs), notification permission and exact timing, "Send a test reminder" | `reveal`: the button |
| Reminders, health sync and calendar import while off; journal lock; Android device backup; developer mode; "Enable decay" | `reveal`: the switch (each opens an Android dialog, a biometric prompt, an asynchronous plugin call, or belongs to a form or a core-save tool kept web in phase 1) |
| Data management (export, report, import, reset, delete) and the voice log's Export and Clear | `reveal`: the button |

The native tabs' switches are the trap of this tab: they are bound to the same boxes as on the page, so the command runs the same `setNativeXEnabled` (spied on in the test), none of which opens its screen while the view is Settings; after each the hand-over's safety net (`NativeTabs.heal`) runs, and the test and the hand-over simulation check that no native tab is left over Settings. Turning Native Settings off from the screen closes it and leaves the classic page; turning it on from the page opens the screen at once. A native tab's gear now hands over to native Settings (make-before-break), and `lmaLeaveNative`, which leaves a native tab for Settings before a reload, raises `lmaReloading` so that native Settings (and so any screen) stays closed until the page reloads. Covering rules besides those above: the tab previews' capture and a page about to reload.

## Settings, phase 1, step 2 of 4: the native screen (next Native API)

`NativeSettingsPlugin` (`ComposeTabPlugin`, tab `settings`, `settings.projection.v1`, registered in `MainActivity`, `nativePlugin` in the catalog) draws the projection of step 1 with no rule of its own. Composition root `app/SettingsContainer.kt`; `feature/settings/{domain,data,presentation}`.

- **Decoder** (`WebSettingsRepository`): rejects a projection whole and keeps the last good one for a missing or mistyped field (a boolean sent as text included, which org.json's `getBoolean` would take), a palette without every token (`core/data/PageJson.kt`, the same file as on track/integ, so the two merge as one), an unknown kind of row or control, a control operated in a way its kind is not (a field is only revealed, a switch only toggled or revealed), two cards or two controls with one id (the list's keys and the commands' targets), a selected or card category the chips do not have, a profile picture that is not a data URL, a notice numbered 0. It draws what is only the page's state of the moment: a select with no options yet (Card art is filled after a timeout), a form field whose inputs are hidden. Older sequences and other sessions are ignored as in every tab.
- **View model** (`SettingsViewModel`): a tap becomes the command or the reveal the projection names for that control. A switch, select or the haptic strength shows the state asked for, faded, and takes no tap until the page answers; the answer arrives with the fresh projection, which is then the truth (a refusal shows the page's state again, with the page's words). A chip is selected at once and the page told; the page's chip shows again if it refuses. Every non-empty reply message and each page notice id is shown once as core `PageToast`; a reply's `reveal` hands the switch to the page. An answer lost on the way stops holding its control after 5 s; opening again forgets what the page will not answer and drops an action of the last opening not yet handed over. After a closing action (a reveal, Classic Settings) the screen takes no tap until it opens again, so a second quick tap cannot follow the first to the page.
- **Screen** (`SettingsScreen`): the head, the chips (scrolling the selected one into view), the Classic Settings card, then every card of the selected category and of none, in the page's order. Each row is an item of the `LazyColumn`, keyed by its first control's id (a bar row by its box, so a moved tab keeps its item) or by its place in its card, and each card is drawn in a piece per row that joins into one card with one border and one shadow. The spaces between rows are the page's, worked out as CSS works them out with margins collapsing (`rowBoxes`, unit-tested). Rows: `.settingsline` (words left, controls right, the controls under the words when they need more than three fifths of the row), the profile picture's row, `.note` and its warning form, muted text, controls on their own, form fields, bottom-bar rows. Controls: the page's tick box (core `PageCheck`, new), LMA_IN selects as wide as their widest option with a native drop-down, the haptic strength as small radio buttons, fields that show their value (times as the phone's browser writes them) and hand the tap to the page, the 64 dp avatar, `.btn` in its primary, secondary, danger, small and disabled forms, the bar's ◀ ▶.
- **Accessibility**: a row whose only control is a switch is the switch (core `Modifier.toggleTarget`, new: `Role.Switch` with its state, at least 48 dp), read by the page's label with the hint after it, with "Turning on/off" while waiting and "opens on the page" for a switch the page keeps; a bar row's box is a switch of its own by the page's "Show Overview in the bar"; selects are drop-down lists with their value; fields say their label and value and that a tap edits on the page; the strength is a group of radio buttons; chips are tabs; headings for the page title and each card title; regular buttons are 48 dp (core `tapTarget`).
- **Core additions**: `PageCheck` (with a Gallery section, dark, light and large text), `Modifier.toggleTarget` beside `tapTarget`, and `core/data/PageJson.kt` (identical to track/integ's).

Evidence: `SettingsTest` (21 tests: the four fixtures decoded, 40 malformed variants each keeping the last good projection, the page's state of the moment accepted, the view model's commands, refusals, reveals, chips, lost answers, toasts and reopening, the wire shapes, the row keys and spacing, the clock) and `SettingsScreenshotTest` (23 images: Look & feel dark and light, the bar editor dark and light, the selects, the haptic strength, Phone & sync, the backup warning dark and light, health, notifications dark and light, the profile form dark and light, the XP rules, developer tools and Data management, Voice & journal, a switch waiting for the page, a chip chosen before the page answers, and text at twice the size on the head, the bar and the notifications).

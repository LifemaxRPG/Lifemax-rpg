## Character: first implementation sequence

### C0 — Inventory and deterministic fixtures

Read current character.html, 01/04/07/14/15-runtime.js, later wrappers, navigation, stores and CSS. Produce CHARACTER_INVENTORY.md identifying exact displayed facts/derived values, chart and comparison modes, selection/sorting, skill progression, avatar, weight/BMI, benchmarks and every action/sheet/navigation path. The eight IDs are physique, endurance, intelligence, business, social, discipline, adventure and wellbeing. Benchmark addition is visibly present in the baseline; inventory its complete handler path and any generated attribute-detail actions rather than claiming Character has no mutations.

Use synthetic fixtures for new, established and legacy/ascended states, plus missing/custom/large-history cases. Do not publish personal saves. Measure fixture size and storage headroom; no 5-MB quota assumption is a substitute for handling actual write failure. Capture the current visual and interaction baseline.

### C1 — Build and native foundations

Register direct authored source/test roots idempotently and verify compile/test discovery, inclusion once and rename/removal behavior. Use the existing Compose setup. Add only required theme primitives, manual composition root and one MainActivity destination host coordinated with existing navigation. Preserve existing APK signing, package identity and update flow.

### C2 — Read-only native Character prototype

Finalize the static character projection schema from C0. Implement capability/readiness negotiation, full snapshots and session/projection-sequence freshness through a feature-owned repository and lifecycle-bound transport. No new native gameplay writes or durable bridge metadata solely for this read slice. Snapshot invalidation must observe legacy changes and time-derived values even when durable save revisions do not exist.

Build native charts/cards, selection, comparison and sorting from the authoritative projection and local UI state. Render no Character DOM/captured page in the native presentation. Include loading/error/reconnect states, font scaling, light/dark/accent themes and reduced motion. Native formatting/layout math is allowed; rewards and gameplay calculations remain authoritative.

Integrate behind a persisted native/classic choice with session fallback on unavailable capabilities. An incomplete developer prototype is not a default production replacement. For existing mutating actions, either delegate explicitly to their working web presentation and record that hybrid dependency, or hold default rollout until the native interaction is complete. Never silently omit a button or pretend it saved locally.

### C3 — Lifecycle and acceptance

Verify shared state after real web actions, stale/out-of-order read responses, live/time-sensitive changes, native covering the web authority, navigation/Back, rapid tab changes, background/resume, rotation, process recreation, unreadable/unavailable data and Classic cleanup. Confirm no duplicate hosts, leaks, background render load or transition flash. Record physical-device performance separately from automated/emulator checks.

### C4 — Mutations and full Character interaction parity

Before each native write capability, adopt an operation-specific command/commit/reconciliation design satisfying CONTRACT A14–A15. Audit legacy save handlers and side effects; do not wrap arbitrary global mutations and label them atomic. Test the failure matrix before wiring the control. Replace remaining web sheets/edits and verify both native and existing web consumers observe the same authoritative results without duplicate effects.

Only then label Character native presentation with complete interaction parity. Core authority can still remain web-owned. Retiring that dependency is a separate later cluster cutover.

## Native Character prototype implementation

The `codex/native-character` slice implements Compose presentation behind the opt-in Native Character preview setting (Classic remains default). Models and owner calculations enter through `50-native-character.js`, with a volatile session/sequence and no durable gameplay writes. Kotlin decodes into immutable projections; a feature repository interface and ViewModel own native presentation state. The platform plugin attaches ComposeView to MainActivity and owns its lifecycle references. Main/test roots are registered directly in Gradle. ktfmt 0.53 formatting is checksum-pinned and checked for the new source tree.

Implemented: hero, radar current/previous comparison and selection, attribute sorting/cards, selected detail and spark bars, skills/show-all, benchmark readout and original-handler delegation. Logging, Luck and benchmark editing remain explicit web dependencies. Native ownership, safe mutating commands and complete native interaction parity are NOT implemented. Physical-device testing, restored transient UI state and complete visual/accessibility parity remain rollout gates; do not label this fully migrated Character or enable it by default.

Evidence: Node projection test, JVM selection/sequence/schema tests, Android Compose-in-MainActivity/no-WebView-subtree test and unchanged core-save assertion; reference/native/scroll/light screenshots are emitted by CI for review. Synthetic projection fixture is not a claim of complete raw-save migration fixtures.

## Life Director, phase 2: the dial's handles and its build

The page stays the only writer. Today's projection now carries everything a native dial needs to drag a handle and to play the build, decided by the same code as the web dial (`src/features/life-director/logic.js`), and two commands answer a release with the page's own decisions. The native screen drags the handles, asks, confirms and plays the build on these fields (the native half, below).

| Field (Today, `today.dial` unless named) | What it is | From |
|---|---|---|
| `handles[]` | one per end of every sleep, work, class, appointment or unavailable rule that starts or ends on the day: `key` (`rule\|end\|ymd\|epoch`, what a release names; a new key whenever the rule moves), `rule`, `end` (`start`, `end`), `kind` (`sleep`, `work`: its colour), `a`, `minute`, `label` (the centre's kick: "Bedtime", "Work ends"), `aria` (the web handle's label: "Bedtime 11:00 PM"), `lengths` (one per stop: the centre's line under the time, "7h 30m of sleep", the length letting go there gives the rule as the confirmation and Change it read it (`dialChange`), so a bedtime held past midnight is the sleep left before the wake-up time; "" under 15 minutes, which the page shows as "Too short" with no arc) and `ends` (one per stop: the angle where the lit span ends, from the stop that long towards the rule's other end in wall-clock minutes, kept on the day as every arc is) | `dialHandles`, `dragPreview` |
| `stops[]` | every place a handle can land, in dial order: `m` (minute of the day), `a` (where the handle sits), `from` (the angle from which the finger picks it, up to the next stop's), `time` (the centre's big time) | `dialStops`, the page's snap (`snapEp`: the nearest quarter hour of the day, never past 11:45 PM), asked wherever the local minute can change, so a day whose clocks change is right too |
| `dragWords` | `tooShort` ("Too short"), `release` ("Release to apply") | `DRAG_WORDS` |
| `build` | null, or the latest build or repair as `runBuild` plays it: `id`, `mode`, `full`, `sweep` (`ms`, `kick`, `readout[]` of `{a, hour, what}`), `intro`, `start`, `items[]` (`id`, `kind` new or moved, `a0`, `a1`, `from`, `at`, `ms`, `land`), `keep[]`, `flips[]`, `ghosts[]`, `lock`, `end`; times in ms from the start | `buildPlan`, shared with `runBuild` |
| `today.hint` | the words under the dial, the handle's pip drawn between the two | `DIAL_HINT`, shared with `renderToday` |
| `reducedMotion` (frame) | the page's reduced-motion reading; `build` is then null, as the page plays none | `reduced()` |

| Command | Payload | Reply |
|---|---|---|
| `dialDrop` | `{key, minute}` (a stop's `m`) or `{key, step}` (1 or -1: a quarter hour later or earlier, as the web handle's arrow keys) | `{ok, changed, confirm}`: what the page's confirmation says (`dialConfirm`: `title`, `from`, `to`, `problem`, `body`, `note`, `apply`, `keep`); `changed: false` where the handle already is; refused for a handle not on the dial (its rule changed), a minute that is not a stop, or while the page is not showing Today with nothing over it (`showing()`, the state the screen covers). Holds and saves nothing, so Keep needs no command |
| `dialApply` | the same | the page's Change it (`applyDial`: the rule changes, the plan is repaired around it, the save): `{ok, changed, moved, message}`, ok only once saved, changed once the rule changed (also when the save then fails: it stays changed in memory, as on the page), moved when sessions moved, `message` the page's notice or, when the save fails, its "Not saved" banner (the page then shows no "now 10:30 PM" message under it, on the web or in the frame); refused, changing nothing, for a change with a problem (the page offers only OK there), a stale handle, a minute that is not a stop, or while the page is not showing Today with nothing over it (Change it closes the page's sheet, so it would close one the user had opened since). A repeat names a handle that has moved and is refused, so the save changes once. The reply's projection has the new plan and its build |

The capability is `director.today.v2` on both sides (v1 was phase 1's Today): a v2 decoder requires the new fields and a v1 page has no dial commands, so a page and an app of different phases do not open the screen and the page stays (A19 already discards a cached page older than the app).

Why stops and lengths rather than a preview command: every NativeTabKit reply carries a whole projection (the tokens and bars with it), and a round trip under the finger would lag; the stops and lengths are the page's answer for every place a handle can land (about 11 KB a day), so the screen looks a drag up and copies no rule (snapping, the 11:45 PM clamp, the 15-minute minimum, the sleep and work limits of the confirmation, the repair).

The build: while the native screen covers Today the page plays none of its own (`LifeDirector.native.coveredBy`), and one already playing stops when the screen opens over it (`cover()`, from `afterOpen`): after a delegated tap that re-plans (Re-plan, Skip in the session sheet), the page starts its build, the screen comes back and plays the same plan from the start. The screen plays each `id` once; ids rise with the clock, so they are not repeated after a page reload. A tap that earns XP still closes the screen and its celebration plays on the page first (`afterCelebrations`); the build plays when the screen is back. The page has no undo for a dial change (its confirmation's Keep, then dragging back), so there is no undo to keep working.

`NativeTabKit.create` gains three optional settings, used only by Life Director so every other tab behaves as before (their web tests and the hand-over simulation prove it): `warm: true` asks the native side what it draws (the handshake) as soon as the tab is enabled and calls `revisit()` when it answers, `has(capability)` reads that cached answer (false until then), and a command whose renders leave the view on something `blocked()` counts steps the screen aside as soon as its reply is sent; `arrive()` runs when the page goes to the tab's view from elsewhere, just before it shows. The plan (plans/LIFE_DIRECTOR_3_4.md section 3.3) made the first two defaults for every tab; they are opt-in here so no other tab changes. The A26 exception for logic.js is in BACKLOG.md.

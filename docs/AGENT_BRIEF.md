# Brief for an outside coding agent: one logic area at a time

You will be given a task in the form of section 8. This brief and the files it points to are all you need. Read the brief
once, then read the area's spec in full before you write any code.

## 1. The product and the phase

LifeMax is a single-user life RPG for Android: the owner logs real activities (training, study, sleep, money, food) and earns
XP, levels, quests and Sparks for them. It is a web app (`lifemax_modular_v73`, plain JavaScript) inside a Capacitor shell, and
some tabs are drawn by native Kotlin/Compose screens.

- **Now (visual phase).** The web page owns every rule and is the only writer of the save. Native screens draw what the page
  sends them and hand taps back.
- **Being prepared (logic phase).** Each area of rules is rewritten in Kotlin from a written spec, not translated from the
  JavaScript. Each area has a spec (`docs/specs/<AREA>_SPEC.md`), golden input/output cases recorded from the real page
  (`lifemax_modular_v73/tests/fixtures/<area>-golden.json`), and a pure Kotlin module that is accepted only when it reproduces
  every golden case.
- **Later, not your job.** A cutover makes the Kotlin the writer. The owner decides it once backups, a single commit path and
  recovery are in place (`docs/architecture/CONTRACT.md` A10, `docs/architecture/decisions/0004-*`). Until then nothing you
  write is called by the app.

**Your job:** you are given the spec and the golden file for one area. Write that area's Kotlin module, and a JUnit test that
runs every golden case against it.

The Gradle project (`android-wrapper/android`) is generated by the first build and ignored by git. It compiles the Kotlin
straight from `android-wrapper/native/src` (main and test). Kotlin 2.0.21, JVM target 21, compileSdk 35, minSdk 26 (so
`java.time` is available). Test libraries: JUnit 4.13.2 and `org.json` (tests only). Do not add dependencies.

## 3. Hard rules

1. **The page is the only writer.** Change nothing under `lifemax_modular_v73/`, and do not wire your module into the app: no
   plugin, no screen, no call from existing code.
2. **The spec and the golden file are fixed inputs.** Do not edit, regenerate or "fix" them. When the spec and a golden case
   disagree, the golden case is right, because it is the page's real output. When neither settles a question, you may read the
   `file:line` the spec cites. In both cases, list the question in the PR (section 7).
3. **Reproduce today's behaviour, defects included.** A rule marked `[Dnn]` is a known bug or accident that the app still
   does. Implement it as described and say so in a comment (`// D05: the whole bonus is spent even when the cap cuts it`).
   Do not fix new oddities either. Report them.
4. **Write from the spec, not from the JavaScript.** Do not translate functions line by line. Do not carry JavaScript names
   (`ecoAward`, `lmvLogXp`) into the module. Name things in the spec's words (`award`, `restedBonus`, `dailyCap`). Page
   function names appear only in the test's adapter table (section 4).
5. **Pure Kotlin.** Main code under `core/<area>/` imports only `kotlin.*` and `java.*` (`java.time` for dates). That means no
   `android.*`, `androidx.*`, `org.json`, Capacitor or Compose. No I/O, no global or mutable singleton state, and no
   `System.currentTimeMillis()`, `ZoneId.systemDefault()` or unseeded `Random`. The clock, the time zone, ids, random
   numbers, and anything a plugin, a dialog or storage would supply are parameters. Messages, records and the new state are
   return values. Use immutable types (`data class`, `copy`). Decoding JSON is the tests' job.
6. **Numbers work as they do in the page.** JavaScript numbers are IEEE-754 binary64, so:
   - use `Double`, and keep the spec's order of operations and its decimal constants exactly as written;
   - round with `roundToLong()` or `Math.round`, which break ties toward positive infinity like JavaScript `Math.round`;
   - never use `kotlin.math.round` (it breaks ties to even) or `BigDecimal`.

   The spec's section on numbers and its numeric-hazards section are binding.
7. **File size and naming.** No file, main or test, is longer than 600 lines. Split by concept, roughly one file per part of
   the spec. Do not create `Utils`, `Helpers` or `Manager` files: a type's name says what it owns. Each public declaration
   has a KDoc comment that cites the rule IDs it implements (`/** CAP-1, CAP-2: ... */`).
8. **Formatting.** Format every file you add with ktfmt 0.53 and `--kotlinlang-style` (section 6).
9. **One area per branch.** Change only these folders:
   - `android-wrapper/native/src/main/java/com/lifemax/rpg/core/<area>/`
   - `android-wrapper/native/src/test/java/com/lifemax/rpg/core/<area>/`
   - `android-wrapper/native/src/test/java/com/lifemax/rpg/core/golden/`, only to create it if it does not exist yet

   If anything else seems to need a change (a dependency, the build, another area, an existing file), do not change it.
   Explain it in the PR. Do not reformat or tidy files you did not write.
10. **Never commit `lifemax_modular_v73/dist/`.** The Android build rewrites it. Run `git checkout -- lifemax_modular_v73/dist`
    before you commit. `android-wrapper/android`, `www` and `node_modules` are ignored by git.
11. **Do not edit `android-wrapper/native/NativeApi.java`.** The owner raises it when merging.
12. **No model names, and plain commit messages.**
    - Code, comments and docs never name a model, an assistant or a tool.
    - A commit subject is one plain-English line that says what is now true, with the area first when that helps (for
      example `Economy: rested XP and the daily cap, with their golden cases passing`). No `feat:`-style tags and no
      trailing period.
    - The body says briefly what changed and why, and cites rule IDs and case ids.
    - Add no attribution trailers.
    - Commit in coherent steps. Every commit compiles and is formatted.

## 4. The golden cases, and how the tests load them

The reference definition of the case format is the header comment of `lifemax_modular_v73/tools/gen_<area>_golden.js`. Read it
in full. In outline:

```
{"id": "award/empty-day", "rule": "AWARD-1",
 "input":  {"now": "2026-10-28T12:00:00.000Z", "zone": "UTC", "state": {},
            "calls": [{"fn": "ecoAward", "args": ["reading", 24, 30, {"manual": true}]}]},
 "output": {"returns": [{"xp": 24, "msg": ""}], "state": {}}}
```

- **`input.state`.** It lists only the save fields that differ from the fresh save. The fresh save is the input state of the
  first case (`fresh/save`): build each case's state by laying its fields over the fresh save. Pure cases have only `calls`
  and `returns`.
- **`fn` and `env`.** `fn` is the page's name for a function (or a constant). `env` is what the page would read around the
  call: a failed save, plugin records, a dialog's answer, the values in input fields.
- **The adapter table.** The test has one entry per page name. Each entry turns `args` and `env` into a call on your module,
  and turns the result back into JSON. A name with no entry fails its case.
- **`output.state`.** These are the save fields the calls changed, with their values afterwards. Compute them the way the
  generator does: encode the state before and after the calls and compare. `deleted` names the fields the calls removed.
  `toasts` are the messages the page showed, in order and exactly as written, Unicode included.
- **Equality** is JSON-value equality:
  - object key order is ignored; array order is not;
  - strings must match exactly;
  - numbers must match exactly as binary64, never within a tolerance. `org.json` returns decimals as `BigDecimal`, so compare
    numbers as `n.toString().toDouble()`.

  Port `same` and `firstDifference` from `lifemax_modular_v73/tests/<area>-golden.test.js`, so that a failure names the
  path and both values.

**Loading.** The golden file is read in place from the repository. Never copy it into test resources. Gradle runs unit tests
in `android-wrapper/android/app`, so the shared loader walks up from the working directory:

```kotlin
package com.lifemax.rpg.core.golden

import java.io.File
import org.json.JSONArray

/** Golden cases, read in place from lifemax_modular_v73/tests/fixtures. */
object GoldenFiles {
    fun read(name: String): JSONArray {
        val start = File(System.getProperty("user.dir")).absoluteFile
        val file =
            generateSequence(start) { it.parentFile }
                .map { File(it, "lifemax_modular_v73/tests/fixtures/$name") }
                .firstOrNull { it.isFile } ?: error("$name not found above $start")
        return JSONArray(file.readText())
    }
}
```

The first area creates `core/golden/` (this loader and the JSON comparison). Later areas reuse it unchanged.

**Test shape.**
- Use one JUnit 4 `Parameterized` test per golden case, named by the case id (`@Parameters(name = "{0}")`), so the report
  lists every case.
- Do not use `@Ignore`, a skip list or `assumeTrue`.
- Add one more test that checks the number of cases run equals the number of cases in the file.
- The spec's notes on recording may say that some fields can be ignored or compared loosely. Leave those fields out by name,
  in one list in the test, each with the spec section that allows it. Leave out fields only, never whole cases.

**Gradle and the golden file.** The golden file is not a declared Gradle input, so Gradle can report the test task as up to
date after the file has changed. Always run your tests with `--rerun`.

## 5. Definition of done

1. Every case in the golden file runs as its own JUnit test and passes. The case-count test passes.
2. `tools/build_android_local.sh` in full mode passes: the app assembles, every unit test in the project passes, and the
   screenshot comparison is unchanged.
3. `python3 tools/check_native_format.py /tmp/ktfmt.jar` passes.
4. All of these hold:
   - no file is over 600 lines;
   - the import check in section 6 prints nothing;
   - `git diff --stat <base>..HEAD` lists only the paths rule 9 allows;
   - no commit contains `dist/`.
5. The PR description is filled in (section 7).

## 6. Commands

**Set-up, once.** Install Java 21, Node 22 and Python 3. Install an Android SDK with `platform-tools`, `platforms;android-35`,
`platforms;android-34` and `build-tools;34.0.0`, and accept the licences with `sdkmanager --licenses`. `tools/LOCAL_BUILD.md`
covers proxies and mirrors.

**Build and test.**

```
export ANDROID_HOME=<sdk folder>
# First run creates android-wrapper/android. Compiles the Kotlin only.
tools/build_android_local.sh compile
# Your tests. Report: android-wrapper/android/app/build/reports/tests/testDebugUnitTest/index.html
(cd android-wrapper/android && ./gradlew :app:testDebugUnitTest --tests 'com.lifemax.rpg.core.<area>.*' --rerun --console=plain)
# Full build, what CI runs: assemble, every unit test, screenshot comparison.
tools/build_android_local.sh
# After any build.
git checkout -- lifemax_modular_v73/dist
```

**Format.**

```
curl -fsSL https://repo.maven.apache.org/maven2/com/facebook/ktfmt/0.53/ktfmt-0.53-jar-with-dependencies.jar -o /tmp/ktfmt.jar
echo '76d05c614fe1864788557170fe89410f75134866a9f84011f9bd570ca12526b1  /tmp/ktfmt.jar' | sha256sum --check
# Format your files.
java -jar /tmp/ktfmt.jar --kotlinlang-style <your .kt files>
# Check every Kotlin file, as CI does.
python3 tools/check_native_format.py /tmp/ktfmt.jar
```

**Rule checks.**

```
# Must print nothing.
grep -rnE '^import (android|androidx|org\.json|com\.getcapacitor)\.' android-wrapper/native/src/main/java/com/lifemax/rpg/core/<area>
# Each file at most 600 lines.
find android-wrapper/native/src -path '*/core/<area>/*' -name '*.kt' | xargs wc -l | sort -n | tail -3
```

CI does not run on your branch. Run all of these yourself, and put the results in the PR.

## 7. The pull request

The title names the area and what is now true. The description has these parts:

- **Golden:** `N of N cases pass`, with the command and the last lines of its output.
- **Checks:** the full build and the format check, with their last lines.
- **Module:** the public API in a few lines, and the list of files.
- **Spec gaps and questions:** for each one, the case id and rule ID, what was unclear, and what you did.
- **Oddities:** behaviour you found that the spec does not list as a defect.
- **Cost:** wall-clock time, and how many full builds it took.

### Worked example: XP and the economy

```
Area:     XP and the economy
Spec:     docs/specs/ECONOMY_SPEC.md
Golden:   lifemax_modular_v73/tests/fixtures/economy-golden.json   (format: lifemax_modular_v73/tools/gen_economy_golden.js)
Package:  core/economy   (com.lifemax.rpg.core.economy)
Branch:   logic/economy, from <commit>
Notes:    as below
```

**The spec.** It has 110 rule IDs and 37 defects (D01 to D37). Its section 1 sets the boundary:

- **In:** level curves, XP derived from the activity ledger, scoring, the award pipeline, rested XP, the daily cap, the split
  and stars, every award path, Sparks, perks, ascension, decay, streak and shields, the migration, the save pipeline, and undo.
- **Contracts only:** the Daily Hand, Life Director scheduling, Health Connect reading, voice parsing and similar. The trigger
  stays outside, and the award rule is in.
- **Out:** rendering, badges, titles, catalogue content, and storage.

**What to read first.**

- Section 0: numbers, dates and strings.
- Section 19: numeric hazards. For example, `round(45 * 0.7)` is 31, not 32.
- Section 20: the defects you must reproduce.
- Section 21: notes on recording, including the fields that may be compared loosely.

**The golden file.** It has 880 cases in 37 families (`cap/`, `preview/`, `curve/`, `health/`, `quest/`, `director/` and
others). 600 cases carry a state and 280 are pure.

- **Before the calls run,** each case's state is completed as `load()` would leave it: the rules are the defaults merged
  with `customRules`, and attribute and skill XP are rebuilt from the ledger. The 5 cases marked `stale` skip that rebuild.
- **The cases call 86 page names** (functions, and constants such as `ECO`), so the adapter table needs all 86.
- **74 cases pass an `env`:** mostly `health`, then `dom`, `failSave`, `stored`, `prompt` and `confirm`.

**Clocks.** Most cases run at 2026-10-28T12:00Z in UTC. Nine `zone/` and `time/` cases run in America/New_York, across the
end of daylight saving time on 2026-11-01. Day keys come from the zone the case gives, never from the machine's zone.

**A possible split, by spec section.**

- Main code: `Curves.kt` (4), `Ledger.kt` (5), `Scoring.kt` (6), `AwardPipeline.kt` (7 to 10), one file per family of award
  paths (11), `Sparks.kt` (12 to 14), `Decay.kt` (15, 16), `SavePipeline.kt` (17, 18), and the save types these files share.
- Tests: `EconomyGoldenTest.kt`, `EconomyStateJson.kt` (golden JSON to and from the module's types), and adapter files split
  by family.
